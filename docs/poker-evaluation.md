# Independent six-max poker evaluation

Implementation baseline: application `96db76540f2bb48f6eb35d15a426f78c8bf0dd1d`, DuelLoop 0.2.1 contracts. This document precedes implementation. The refactor plan's cost admission limits conflict with the owner's explicit no-budget-gates requirement: evaluation records actual usage and unknown costs without monetary admission gates.

The evaluator plays independent six-seat no-limit Texas Hold'em hands. Each hand starts with the protocol's fixed integer stacks; the button rotates; small/big blinds are fixed. There is no rake, ante, straddle, tournament elimination, running twice, or mid-hand join. This is a controlled cash-game experiment, not a replica of the OpenPoker lobby or season economy. Profit is settled chip change normalized as bb/100; rebuy grants and season scores are excluded.

Rules include calls capped by remaining chips, raise-to totals, full-raise reopening, cumulative short all-ins, side-pot eligibility, unmatched wager returns, ties and clockwise odd-chip allocation. A complete shuffled deck is fixed before either strategy acts. Each policy executes its own branch to settlement. Each actor receives only its private cards, public board and past actions. Full decks, other private cards and future board cards never enter decision features.

Randomness is keyed independently by seed block, hand index and purpose: deck, initial seating, per-opponent action and candidate sampling. Different action counts cannot consume the deck or another actor's random stream. Opponent suites have immutable versioned IDs and multiple distinct archetypes; scripted opponents validate a fixed benchmark population, not optimal play or all possible public bots.

The adapter and live coordinator use `buildPokerContext()` for hand-local behavioral input, followed by the same fact/candidate projection, SDK question construction and Score aggregation. A hand begins with `session.turn=1` and empty `previousChoices`. Each independent baseline/candidate branch maintains its own history, adding an accepted Jev choice only after the environment applies the action. Later decisions include the last six earlier choices; the turn ordinal counts the full hand history. Live history retains its stored accepted, failed and cancelled statuses; failed/cancelled records do not imply an executed action. Each hero decision calls the supplied DecisionModel, including single-candidate decisions. Model failure, cancellation, identity mismatch or deadline expiry aborts the experiment; no fallback action receives a reward. Fixtures test rules and accounting only and are explicitly identified as fixtures. The SDK's modelCalls counts score invocations; provider retry attempts are independently recorded by transport accounting and are not mislabeled as score calls.

The session correction uses feature contract `visible-poker-facts-v4`, feature builder `visible-facts-priced-actions-session-v4`, continuation `same-release-current-visible-state-session-v2`, and evaluator identity `poker-six-max-session-v2`. Poker rules and opponent suites are unchanged. Reports created under the earlier session-less evaluation contract remain historical artifacts and cannot validate the corrected runtime.

Development and final protocols must have different holdout IDs and disjoint seed sets. The immutable protocol fixes suite, stacks, metric, independent sample count, confidence, improvement/regression and latency thresholds before validation. The DuelLoop store enforces holdout reuse limits. `online_update` is rejected until an identical live knowledge update contract is provided; the initial evaluator uses frozen facts only. Model results from a few hands demonstrate integration, never profitability. Independent statistical samples are seed blocks, not hero decisions or hands inside a block.

The simulator must pass deterministic settlement, visibility, branch and conservation tests before real model evaluation. Actual OpenPoker conformance is limited to the currently implemented server-visible no-limit action/raise-to semantics; this document does not claim certification by OpenPoker or exact equivalence for unobserved edge cases.

Rule review cross-checks the [Poker TDA raise and reopening examples](https://www.pokertda.com/view-poker-tda-rules/) and [PokerKit's minimum-raise implementation](https://github.com/uoftcprg/pokerkit/blob/master/pokerkit/state.py). An opening all-in of 5 with a 10 minimum requires a raise to at least 15; limit-poker completion to 10 is not offered. These references do not establish OpenPoker certification.

The exported pilot protocol has four independent blocks and requires at least thirty, so it cannot qualify a release. Its public diagnostic seeds are not a private final holdout. Formal research must load independently frozen development/final protocol files with sufficient samples and protected final seeds. Softmax evaluation requires a release-bound random seed and uses the SDK's trajectory/revision sampling contract.

A historical integration diagnostic on 2026-09-24, before the session correction, used the configured Jev model through the audited model adapter: two seed blocks, three hands per policy per block, one mixed opponent group, identical baseline and candidate strategy, twelve simulated hands total. All 36 hero decisions made a real model request; 36 transport attempts completed. Token accounting reported 349,626 input and 4,732 output tokens; dollar cost was not provided and remains unknown. Observed local preparation plus model decision latency was approximately 908 ms p50 and 1,978 ms p95. The SDK report was **inconclusive** because independent samples, improvement and group non-regression were not established. It is evidence of the earlier model transport integration, not validation of the corrected session contract, profitability or deployment readiness. The private detailed report lives under ignored `data/reviews/duelloop-refactor/`.
