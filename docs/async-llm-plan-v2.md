# jev-card-agent 下一轮实施方案 v2

## Jev 实时决策 + 异步 LLM 研究 + 可验证的知识发布

**日期：2026-09-22。文档版本：v2；不是应用版本。**

本方案替代上一版“先不接 LLM”的范围约定。当前核对的 master 为 `12ab7a3508fff79893dd834e94cde686284f20fb`（1.2.4）；开始实现时再次记录 HEAD，保留已完成的双循环和中途入座修复，不重复实现已有工作。[S1]

本文是实施与验收方案，不是已完成实现、已执行实验、已上线或已盈利的报告。新增配置、命令、表和类型都是建议合同，不是当前仓库已有能力。

## 1. 本轮必须交付的结果

本轮不是只增加 LLM 接口、聊天分析或复盘页面，而是交付以下完整链路：

```text
已经完成且可用的历史证据
  → 后台 LLM 研究
  → 结构化提案
  → 证据与发布校验
  → 已发布的简短建议
  → 下一手固定知识包
  → 实际 Jev 请求采用
  → 决策/延迟/收益的独立评估
```

**验收终点：至少一项经过审核或既定发布策略批准的 LLM 建议，可追溯地进入后续手牌的实际 Jev 请求。只在数据库产生 proposal，不算本轮完成。**

工程验收可以用受控响应覆盖完整链路；真实供应商诊断与真实 Arena 生效必须分别显式启动，并在报告中区分。制定方案不授权消费 API、入桌、部署生产或写入仓库。

本轮保持实时动作由 Jev 最终选择，正常动作路径只发起一次 Jev 请求。LLM 不在行动期限内串行参与，Jev 不等待研究。无需 pi 重构，不实现新扑克服务器、完整 GTO 求解器或自动代码改写。

原方案里的 Worker 恢复、知识新鲜度和必要缓存继续保留，但作为这条链路的支撑工作；不能用完成这些工程项目替代 LLM 真正可被采用的交付。

## 3. 两个逻辑循环，三个独立执行职责

```text
                         快循环
OpenPoker 事件 → 可信状态/当前事实 → 固定知识包 → Jev → 执行校验 → 提交
      │                                  ↑
      ▼                                  │ 无等待读取
原始事件与冻结决策                     本地已归档发布包
      │                                  ↑
      ├→ 统计 Worker → 确定性统计 ────────┤
      │                                  │
      └→ EvidenceBuilder → 研究调度器     │
                             ↓           │
                          LLM Worker     │
                             ↓           │
                     Proposal / Validator
                             ↓
                  Approved advice / Publisher
```

逻辑上仍是快、慢双循环。慢循环内部，统计计算与 LLM 研究必须分开执行：不能在 `StatsWorker.tick()` 中等待远程 LLM，也不能让长分析阻止统计快照发布。

### 3.1 快循环不变量

1. 最新牌面、当前手行动线和合法动作来自服务端状态；LLM 不能修改这些事实。
2. 本地计算牌型、价格、边池资格、有效筹码等已实现事实。LLM 不能生成一个未经验证的 equity/EV 数字替换计算结果。
3. 下一手开始时固定基础规则、统计快照、建议集合、筛选策略和实验模式；本手内只更新当前局面。
4. 根据固定建议中的结构化 scope 做本地匹配，最多传入少量相关内容；没有命中就不传。
5. Jev 做最终候选选择；执行代码严格校验授权、状态、金额和期限。
6. LLM 超时、宕机、限流、结果无效、尚未发布，只阻止该新建议被采用；已有且仍合格的固定知识继续使用，不触发实时等待或本地代打。
7. Jev 自身失败仍沿用原持久停牌机制；研究自动恢复不能触发牌桌 resume。

### 3.2 凭据与数据边界

统计 Worker 继续不接收模型或牌桌凭据。研究执行单元只接收允许的 LLM 配置、已冻结的脱敏证据和任务元数据，不持有 OpenPoker/Jev 的操作凭据，也不暴露 submitAction、resume、shell 或代码执行能力。

可以使用单独 Worker 或进程；不要把线程当成运行不可信代码的安全沙箱。首版 LLM 仅返回数据，不执行任意工具调用或模型生成脚本。未来真需要工具时再增加白名单数据接口，不因此引入 coding-agent Runtime。

## 4. LLM 首轮只做两类研究

### 4.1 对手条件化摘要：opponent_brief

输入为限定窗口的已完成手牌、代码计算的机会数/次数、行动线路和公开摊牌示例。LLM 的工作是综合这些证据、提出有限范围的假设、指出反例和适用边界，而不是重新统计数字。

输出应回答：在哪种街道、底池类型、筹码深度或下注条件下，观察到了什么；证据支持到什么程度；遇到什么情况不能外推；哪类现有策略原则值得在此条件下优先考虑。

例如“翻前参与较宽”不能自动变成“河牌大注多数是诈唬”；无摊牌不能作为诈唬证据。必须保留选择偏差、未知价格及样本不足说明。

### 4.2 自身重复问题复盘：leak_review

在分层采样的完整历史上识别重复的决策问题：弱牌面对大额风险时的依据是否不足、强牌价值下注是否被遗漏、相关证据是否未进入请求、规则和候选描述是否矛盾等。

输入必须包含普通、盈利、亏损及零收益手，不能只给最大亏损。分析输出是问题假设、支持和反对证据、需要补充的回归场景、可能的建议，不直接给原动作贴“因为输了所以错误”的标签。

产生的新全局策略建议须进入审批/验证，不能自行修改 BASE_CARDS、候选金额、权重、源码或运行配置。

### 4.3 明确不做

不逐手实时求 LLM 动作，不回头执行已经结束手牌的建议，不构建无限自我反思循环，不让研究模型自评通过就上线，不承诺经过 LLM 总结就会盈利。

## 5. 研究输入与结构化输出

### 5.1 ResearchBatch

由可信代码冻结，建议字段：

```text
batchId / taskType / scopeKey
basePolicyVersion / researchPromptVersion / inputSchemaVersion
rulesetVersion / contextSchemaVersion
sourceSnapshotHash / evidenceEventWatermark / cutoff
eligibleHandIds / metricRefs / exampleRefs / counterExampleRefs
sampleDefinition / missingness / disclosureMode
```

同一 batch 不随新手牌到达而变化。研究输入禁止 turn token、操作凭据、控制端点、未来未公开底牌。对手名字可映射成作用域内稳定的匿名键；公开名字不是可验证的真实身份。

逐手复盘将“当时可见信息”和“结算后可见信息”分开。前者用于解释原决策依据，后者只能支持事后分析，不得回填成当时已知信息。

### 5.2 ResearchProposal

以下为合同示意，需补运行时 schema 校验；TypeScript 类型不是安全验证：

```ts
interface ResearchProposalV2 {
  kind: 'opponent_brief' | 'leak_review';
  basePolicyVersion: string;
  evidenceSnapshotHash: string;
  evidenceRefs: string[];
  counterEvidenceRefs: string[];
  scope: ResearchScope; // 白名单结构；不是可执行表达式
  hypothesis: string;
  suggestedGuidance: string;
  metricRefs: string[];
  limitations: string[];
  invalidateWhen: InvalidationCondition[];
  proposedRecipeId?: string;
  requiredScenarios: string[];
}
```

可信代码生成 proposalId、模型元数据、实际接收时间、内容哈希和发布状态。LLM 不能自行赋予 approved、published、可用时间或人工审批签名。

`ResearchScope` 只允许已支持的街道、人数、位置、筹码/下注桶、可验证的对手键、规则和基础策略版本。scope 未匹配的建议不能进入 Jev 请求。参数范围按 schema 和既定策略校验，不执行 LLM 生成的 SQL、JavaScript 或任意谓词。

数值声明尽量引用 metricRefs，由代码把原始值和分母渲染出来。模型自己的 confidence 只标为自述，不当成真实胜率、统计置信度或批准标准。

### 5.3 输出到 Jev 的是短建议，不是完整分析

保留完整输入、响应、提案、校验和审批日志用于私有审计。实时投影只加入已批准建议的适用范围、简短观察、条件化指导、必要限制与样本依据。

建议起始限制为最多 3 条、每条至多约 300 字符，总计约 900 字符，并另设实际序列化 UTF-8 字节上限。字符约束不等于 token；实际 usage 与提示长度单独测量。精确规则由实现定义并版本化，不让审计哈希、长历史 UUID、原始思考文本挤占主要上下文。

检索按 scope、批准状态、新鲜度和显式优先级在本地完成。默认不再增加一次 LLM 检索或额外 Jev 门控请求；记录截断/未命中原因。

## 6. 调度、合并与背压

两秒一手是设计场景，不是每手必须新建一项远程研究任务。按批次研究可复用内容，调度门槛不是统计充分性证明。

以下均为初始可配置值，需按真实供应商和部署测量调整：

| 项目                     | 建议起点                                          |
| ------------------------ | ------------------------------------------------- |
| 对手摘要触发             | 30 手新完成手牌，或 60 秒检查周期且存在足够新证据 |
| 自身重复问题复盘         | 100 手新完成手牌的批次                            |
| 研究并发                 | 1                                                 |
| 全局待处理任务上限       | 8                                                 |
| 每个 taskType + scopeKey | 最多一个执行中任务、一个可合并待处理任务          |
| 单次请求超时             | 60 秒，独立于牌桌期限                             |
| 整项工作期限             | 120 秒，包含有界重试                              |
| 输出上限                 | 可配置；从能容纳结构化提案的有界长度起步          |

没有新证据不重复调用；样本不足允许输出 insufficient_evidence，并记录下一次触发所需条件。原始历史不因队列满而删除。

运行中 batch 保持不可变。新证据只合并到下一个 pending batch；不要每来一手就取消运行中的分析。对手离桌不一定立刻丢弃研究，结果可以服务以后重遇；但不能不检查过期和适用范围。

任务持久化状态建议：pending → running → completed / failed / superseded / cancelled。持久租约、代次和心跳支持恢复；旧执行代次的迟到响应不能写入当前任务结果。

任务幂等键包含类型、scope、证据哈希、基础策略、模型和提示版本。系统可以避免重复发布，但外部 API 在未知响应情况下不一定支持恰好一次调用；不能宣称本地去重就保证不重复计费。取消也不表示供应商没有计费。未知 usage 保持未知。

## 7. 发布：统计事实与 LLM 建议分层

### 7.1 不直接覆盖基础规则

知识包拆分为三个有来源的部分：

```text
BasePolicy          固定、已审核的基础规则
DeterministicFacts  代码计算的统计与事实
ApprovedAdvice      经验证/审批的 LLM 条件化建议
```

保留现有 BASE_CARDS 校验，新增 ProposalValidator / AdviceValidator 和 BundleCompiler。不要只把允许 source 的数组加上 llm 就认为完成了发布设计。[S5]

### 7.2 验证不等于证明策略正确

至少验证：schema、大小、白名单 scope、证据真实性及信息截止、metricRefs 数字与分母、对手/规则匹配、基础策略依赖、重复或已被替代状态、禁止能力、现有回归场景和应用模式。

涉及策略行为时，还要有不由该研究模型独自决定的回归或离线检查。LLM 可以生成候选测试场景，但不能把自己的期望答案自动当成真值。确定性程序能检查结构和已知事实，不能完整证明任意自然语言策略最优。

Jev 官方文档明确提示 state 中的对抗内容可能影响结果。[S9] 提案、对手名称和历史文本作为不可信数据处理；证据引用、结构化条件、固定指令、最小权限和攻击样例测试必须共同使用，不能保证靠一句“忽略注入”解决问题。

### 7.3 同一迭代交付三个运行模式

| 模式   | LLM 是否工作 | 能否进入真实 Jev 输入                |
| ------ | ------------ | ------------------------------------ |
| off    | 否           | 否；保持原有统计输入                 |
| shadow | 是           | 否；生成、验证、存档、做显式离线评估 |
| live   | 是           | 仅采用已经批准并成功发布的建议       |

默认发布配置 off，避免升级自动消费额度；显式启用后可按同一迭代完成 shadow → live。只交付 shadow 而没有批准、发布、消费与撤回路径，不算本轮完整交付。

首次启用 live 需要操作者确认。建议分两种发布策略：

- manual：新的策略类型、自由文本全局规则和未审核 recipe 必须审批后发布。
- approved_recipe：对既有批准模板的局部对手摘要，可在开启该策略后自动刷新。数值来自代码，适用条件、最大内容和失效规则受控；新 recipe 不自动放行。

此设计避免每一条摘要都等人操作，同时不允许模型从零改写全局策略。人工批准/拒绝/撤回通过私有 CLI 或受保护 API，不改变公开只读页面。

### 7.4 版本与有效性

新增独立标识：evidenceWatermark、basePolicyVersion、adviceRevision、publicationSeq、bundleHash。证据水位证明用到了哪些数据，不是策略修订计数；同一证据可产生多个待比较提案。

对同一 scope/topic 的发布使用当前建议版本比较后提交（CAS），防止晚到旧结果覆盖较新建议。全局 publicationSeq 由可信发布器递增，不能由 LLM 指定。当前水位唯一的旧表保持兼容，新合同通过增量表或明确迁移实现。[S6]

**较旧的数据不等于无效建议。** 实际手牌会持续产生，LLM 结果通常晚于最新统计。不能仅因 sourceWatermark < latestWatermark 就拒绝，否则慢循环可能永远无法被采用。

应按基础策略是否仍兼容、建议适用范围、证据年龄、是否出现预定义反证/失效条件、是否已有同主题更新来判断。新统计出现时，代码可验证支持条件是否还成立；不成立就暂停采用或请求新研究，不能静默改写原建议文本和来源。

### 7.5 每手采用与撤回

编译包完成验证及可靠归档后，记录 availableAt。只有 availableAt 不晚于本手准入边界的包可以被新手采用。publicationAt、receivedAt、availableAt 与证据 cutoff 分开保存，不能由较早的模型/远程时间倒填。

例如 h100 固定统计 S12 + 建议 A7；期间发布 A8；h100 继续使用 A7，h101 才可能采用 A8。当前牌面和行动线照常更新。身份晚到只能从本手已固定归档中选择适用内容。

普通撤回只影响后续新手，旧手 pin 和回放保留。哈希损坏、泄漏凭据或无法可靠恢复 pin 等完整性问题不是普通策略更新，应明确失败/按现有机制停牌，不能悄悄换知识掩盖事故。

## 8. 传输层复用与模型配置

现有 ReasoningProvider 的接口绑定当前决策，不能仅在后台调用原 analyze(context, candidates) 就当成批次研究。[S3] 建议抽取模型无关的有限能力客户端，保留：取消、deadline、有界重试、消息/响应解析、requested/actual model、usage 与请求诊断。

新 LlmResearchProvider 负责 ResearchBatch 到结构化提案的转换；使用实际协议支持的结构化输出方式，并始终做本地 schema 校验。不同协议/供应商的 thinking、reasoning 和结构化输出参数不得盲目互传。

首版只接通一套用户已有且经真实探针核验的模型配置，保留模型/协议可配置，不在本方案杜撰最新模型名或保证哪个模型打牌最好。没有提供密钥或实际调用时，只报告适配器/受控测试状态。

区分实时 Jev 调用与 research/evaluation 调用计量。LLM 费用按真实 usage 或明确估算记账；未知不写零。研究账本提交不能依赖一个当前 Arena Run 仍然存在，也不能长时间持有原始数据库写锁。

新研究凭据不发给匿名网页、SQLite 公开导出、牌桌对手或统计 Worker。可以在现有派生库设置 research 专用表和短事务，或者用独立 research.sqlite 降低写争用；最终选型需记录。无论选哪种，LLM 网络等待期间不得持有数据库事务/锁，不能绕过既有原始库的写入边界。

本轮不新增累计金额到阈值就阻止 Jev 请求的逻辑。并发、触发频率、任务大小和重试是工作量约束，不是隐蔽的资金门槛。

```dotenv
LLM_RESEARCH_INTERVAL_MS=60000
LLM_RESEARCH_TIMEOUT_MS=60000
LLM_RESEARCH_JOB_TIMEOUT_MS=120000

# 发布策略与研究开关分开
LLM_ADVICE_PUBLISH_POLICY=manual
# manual | approved_recipe
LLM_ADVICE_MAX_ITEMS=3
```

模型、协议、endpoint、凭据引用、输出长度与推理设置应接入现有配置校验，并在文档标明 research 专用语义。不要自动使用牌桌凭据或示例文件中的占位值发起真实请求。

`actionSource=jev` 与 `knowledgeSource=llm-assisted` 分别记录。live 运行应标为“Jev + 异步 LLM 辅助”，不能只因最终动作由 Jev 选择就把它与完全无 LLM 的评测混为一谈。

## 10. 工程加固：保留必要工作，不阻碍纵向交付

### 10.1 Supervisor

统计与研究执行器分别监督。error/exit 去重、generation 隔离、异常退避、主动停止取消重启、永久配置错误告警、无新证据正常 idle。旧实例确认终止或租约已隔离后才启动接替者，不产生双发布者。

任务重启不得清除持久停牌、重复发牌桌动作或修改当前手 pin。研究故障只影响研究。

### 10.2 归档与缓存

已采用的统计/建议组合须能在派生库重建、缓存清空和进程重启后恢复。内容寻址归档去重，轻量 pin 保存引用；保持原有旧格式和旧哈希不变。

新版本归档后才可采用，pin 与引用要具备崩溃一致性。重复状态消息不传完整大快照；按字节和数量限制缓存。CPU 密集工作不在快路径，LLM I/O 不占统计 tick。

大快照全量优化可以在纵向链路建立后完善；但当前手恢复、批准版本溯源和快路径无等待是交付前置条件。

### 10.3 新鲜度与告警

分别观测统计积压、研究积压、最新建议年龄、各对手证据年龄、采用率和不采用原因。LLM 建议必须有可信代码批准的有效期/证据窗口策略，不能把模型“我很有把握”当成永不过期。

基础统计的新鲜度过滤策略保持版本化；实验中不能因工程升级悄悄改变。控制台必须分清 off、shadow、live、待审批、已发布、未命中、被撤回和过期。

## 11. 本轮主实验：先测 LLM 增量，而非全面六组组合

保留原计划 none/stats/full 作为以后诊断能力，不必在本轮同时开展所有组合。主对照固定当前 full 统计/记忆口径、Jev 模型、基础提示词、候选和数值工具，只改变是否可采用 LLM 建议。

| 组             | 后台 LLM           | Jev 可见 LLM 建议 | 用途                                   |
| -------------- | ------------------ | ----------------- | -------------------------------------- |
| A：现有双循环  | 不运行或不产生影响 | 否                | 参考组                                 |
| B：研究 shadow | 运行               | 否                | 测后台开销与建议质量；不是独立策略变体 |
| C：研究 live   | 运行               | 是，仅批准内容    | 测 LLM 建议的增量                      |

A/B 的预期模型输入内容应一致（审计元数据不进入请求）；不要将模型自身波动误判为研究收益。A/C 才是主策略对照。

### 11.1 免费 prepare 与全链路受控测试

生成固定证据 batch、模拟结构化响应、验证、批准、发布、下一手 pin 和实际 request。覆盖 off/shadow/live，默认测试不发付费请求。先证明真实请求投影有差异且仅差在允许字段，而不是只测 UI。

### 11.2 真实供应商小样本诊断

显式启动后，先用少量批次核对请求协议、模型标识、结构化响应、usage、失败处理和提案落库。再用约 30 个合格冻结决策 × A/C 两种投影作 60 次逻辑 Jev 决策对照；LLM 调用和重试另计。这是 smoke test，不是盈利样本充分性的承诺。

研究证据、开发验证和留出决策按手牌/时间隔离。研究模型不能见到待评估手牌、该手后来公开的对手牌或结算后再给该决策建议。需要修改提案时使用开发集；留出集结果不得回流后仍称为未见测试。

在今天根据较早历史生成、再测试较晚历史的建议，要标为“事后时间切分实验”。即使证据没有越过历史决策时间，建议实际也不是当时已发布；不能伪装为严格的原运行回放。

离线测：输入/提案合法性、证据支持、独立已知错误、动作分歧、请求长度、延迟、调用失败、采用率和模型波动。不得为未执行动作分配原历史收益，也不以另一 LLM 的打分独自证明扑克最优性。

### 11.3 真实 Arena 独立试验

先完成工程门槛，再显式启动 A/C 预注册的平衡时段或手数块轮换，只在手牌边界切换。初期冻结批准建议集合和基础策略，减少一边测试一边改策略的干扰；后续再单独测持续自适应版本。

两组使用相同的数据可见口径、公共展示规则和候选，不用额外账户同桌互打。记录对手组合、时间、规则、盲注和资料来源。共享历史包含混合行为策略影响，不能声称完全独立学习；公开 Arena 的轮换并不消除全部环境混杂。

主结果包含所有可核验分配手牌、模型失败和平台超时；缺失结算另报。按手计算 bb/100，不把 decision 当独立收益样本。区间按会话/时间块处理相关性，样本不足明确说明。

只有影响实际请求才算 adopted；有命中但动作没变不等于无效，有动作改变也不等于更好。报告应允许 LLM 没有增益或增加成本的结论。

## 12. 指标与完成证据

### 12.1 实时性能

收到行动机会到发出动作、发送到 ACK 分开记录；事实准备、知识检索、模型调用、持久化、提交分别测量，避免阶段重叠相加。报告部署硬件和样本数，以及 P50/P95/P99。

验证研究禁用、正常、网络长等待、限流、队列满和崩溃状态。快循环不能等待 LLM，但加入短建议可能增加 Jev 输入成本和响应延迟；不能宣称双循环就必然零开销。

本地准备 P95 争取不超过 50 ms 可作为工程目标，不是已有性能，也不能通过缩短平台合法期限达标。最终按同部署基线和数据比较。

### 12.2 研究与知识

记录任务触发原因、排队/执行时长、覆盖范围、token/cost、未知 usage、无足够证据比例、拒绝原因、批准/发布时间、availableAt、scope 命中率、真实 adopted 率、过期/被替代率、对手证据年龄。

建立端到端 lineage：

```text
event/metric → researchBatch → modelAttempt → proposal
→ validation/approval → advicePublication → bundleHash
→ handPin → JevRequestHash → decision/action/settlement
```

### 12.3 功能完成与效果完成分开

功能完成：真实供应商通路可用、提案可验证发布、后续 Jev 实际能消费、失败不阻塞、记录可重放。没有真实调用授权时，只能报告受控测试完成，不能声称供应商已验证。

效果结论：需要独立实验。短期净赢、几个案例改 fold、schema 通过和模型自评都不构成盈利证明。虚拟筹码和 API 法币费用分别报告，不换算成法币投资回报。

## 15. 迁移、权限、发布与回滚

旧事件、决策、动作、手牌、Run、费用记录、模型请求和已有 pin 不改写。新增研究及发布数据增量迁移，旧哈希和格式继续可读。备份必须包含已经引用的不可变知识归档和研究发布证据；不能只复制正在写入的 SQLite 主文件。

公开底牌/当前手决策展示是现有产品合同，本轮不擅自改变。[S10] 实验记录暴露模式，所有组保持一致；竞技私有信息延迟展示如需更改，应单独确认。

部署前等待当前手结束、官方确认离桌、完成一致备份、检查新旧格式恢复和失败回滚。上线 off → 显式 shadow → 人工确认 live；这些是同一迭代的运行门槛，不是将 LLM 永久延后。

普通撤销建议只影响下一手；无法恢复当前固定依据或状态完整性时按既有停牌机制处理。不得删除原数据库或停牌标记来“恢复成功”。

## 16. 最终交付物

实现与测试；新增迁移/归档/恢复说明；两类 ResearchBatch 与实际结构化响应样例；私有审批/发布/撤回入口；off/shadow/live 配置；端到端 lineage；免费实验 prepare；显式真实诊断和评测入口；原始性能数据；独立的工程、离线、Arena 报告；未验证事项。

**最小闭环演示：**从一组已完成手牌构建研究证据 → 真正调用已配置 LLM（显式启用）→ 形成提案 → 校验/批准 → 发布 → 后续匹配 scope 的手牌固定采用 → 存档的实际 Jev request 含建议 → Jev 仍独立选合法动作。没有这个链路，不把“接好一个模型接口”当成完成。

保留必要 Worker 恢复、归档与缓存，但不把工程加固替代 LLM 可消费的交付。不引入 pi，不做自动代码改写，不删除历史和账本，不增设阻止 Jev 的累计金额门槛。默认只运行无付费测试；真实模型、Arena 和生产部署分别显式启动。报告实际验证与未验证边界，不把结构化正确、动作变化或短期盈利写成长期优势。
